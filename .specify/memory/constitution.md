# Joule Constitution

The five principles below set the bar every feature has to clear. They are
not aspirational. A spec or plan that violates one needs a justification in
the plan's Complexity Tracking table, or the violation gets removed before
the work starts. The principles were chosen because each one has cost the
project time when it was skipped earlier in the build.

## Core Principles

### I. RLS On Day One (NON-NEGOTIABLE)

Every Postgres table ships with row-level security enabled before any code
reads or writes it. A new table without a policy is a security bug, not a
TODO. The service-role client (`getSupabaseAdmin`) is reserved for system
jobs (Stripe webhooks, seed scripts, scheduled tasks) — anything triggered
by an end user runs under the user's auth cookie so the database enforces
the access rules. If a use case seems to need service-role from a user
request path, the right answer is almost always a SQL function or a new
RLS policy, not bypassing RLS.

Rationale: customer data leaks in this kind of app happen because someone
adds a table and forgets the policy, or reaches for the admin client to
ship faster. The cost of writing the policy up front is small. The cost
of finding out you shipped without one is large.

### II. Spec Before Code (Sprint 2 Onward)

For features touching more than one file, a `spec.md` and `plan.md` land
before any implementation does. The spec describes what and why in
business language; the plan describes how in concrete file paths and
trade-offs. Reviewers (the supervisor, peers, future me) read both before
they read the diff. When implementation drifts — and it will — the spec
is updated to match, not the other way around.

Sprint 1 was test-first without separate specs. The cost showed up in
Week 4 when a Stripe webhook integration touched seven files and the
review comment was "I can't tell what this is supposed to do without
reading every file." Spec-first prevents that.

Out of scope: throwaway scripts, single-file fixes, documentation-only
changes. The judgement call is whether a reviewer would understand the
change from the diff alone.

### III. Test Pyramid With Real Coverage Gates

Three layers, each with a numeric gate that fails the build if missed:

- **Unit** (`vitest`): pure functions in `src/lib/**`. Gate: 85% lines,
  75% branches, 80% functions, 85% statements (enforced in CI).
- **Integration / BDD** (`playwright-bdd`): user journeys driven from
  Gherkin. Three sub-layers — L1 deterministic, L2 grounding invariants,
  L3 stochastic tolerance with M-of-N gates for the AI-touched flows.
- **Smoke** (`k6` against the deployed URL): hot routes return 2xx
  under load with `p95 < 3s`, `http_req_failed < 2%`. Runs after every
  deploy to main.

Implementation details (frameworks, runners) can change; the three
layers and the existence of numeric thresholds cannot. A feature that
can't be tested at one of the three layers needs justification in the
plan.

Rationale: tests without thresholds are vibes. The 85% number is the
floor that surfaced real regressions in Week 5; lowering it requires
the same justification as any other constitution violation.

### IV. Tracked Decisions, Tracked Evidence

Architectural decisions live in `docs/architecture-decisions.docx` —
one entry per decision, written in the past tense ("we chose X because
Y, accepting Z"). Experiment outputs live in `docs/experiment-*.md`
with the raw data they're built on. Weekly retros and DORA metrics
live in `docs/weekly/` and `docs/dora.md` and are regenerated by
scripts so they can't drift.

If a future reader asks "why was this built this way?" the answer
should be a file path, not a Slack search.

### V. One Branch Per Week, Squash To Main

Branches are named `week-NN-<theme>`. They get squash-merged into
`main` via PR — one commit per branch, message references the spec.
The portfolio narrative is built around the branch history, so this
rule is what makes the timeline legible. Hotfixes are exceptions and
are called out as such in the commit message.

Direct pushes to `main` are reserved for the supervisor and for the
weekly DORA-report bot.

## Operating Rules

### Code Review

A PR is ready for review when:

1. The spec and plan exist (Principle II).
2. CI passes — unit, lint, typecheck, build (Principle III).
3. RLS policies are visible in the migration diff if any table was
   touched (Principle I).
4. The plan's Complexity Tracking table is empty, or each row has a
   justification a reviewer can push back on.

Reviewers comment on the spec/plan, not just the diff. If the diff
matches the plan and the plan is sound, the diff is sound.

### Spec Drift

When implementation diverges from the spec, the spec is the document
that gets updated. A spec marked "delivered" must match what shipped.
Outdated specs are worse than no specs because they teach the wrong
lessons to whoever reads them next.

### Out-of-Band Work

Hotfixes, dependabot bumps, and operator-only chores (apply migration,
rotate key, etc.) skip the spec/plan gate. They land on `main` with a
commit message that names the principle they're skipping and why.

## Governance

This constitution sits in `.specify/memory/constitution.md` and ships
with the repo. Amendments happen via PR — the amendment commit
message records what changed and why. The version below bumps on
every amendment.

A principle is violated only when no smaller change satisfies the
goal. The plan's Complexity Tracking table is the place to record
the trade-off; reviewers push back there, not in the diff.
